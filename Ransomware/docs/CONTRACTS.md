## SECTION 1 — IDENTIFIERS

Four and only four canonical identifiers exist in this system.
All modules MUST use these exact formats. No abbreviations, no alternatives.

---

### 1.1 `instanceId`

| Field       | Value                                          |
|-------------|------------------------------------------------|
| **Format**  | UUID v4 (8-4-4-4-12 hex, lowercase, hyphenated)|
| **Example** | `f7f1f0f0-4b9d-4b7f-a5a0-3d7dd3d17c12`        |
| **Scope**   | One Pixel Chaser JVM launch                    |
| **Generated by** | Pixel Chaser (GameLifecycleHook) at game start |
| **Lifetime**| From game start → session record persisted     |
| **JSON key**| `instanceId`                                   |

---

### 1.2 `sessionId`

| Field       | Value                                          |
|-------------|------------------------------------------------|
| **Format**  | `SES-` followed by 6 zero-padded decimal digits|
| **Pattern** | `SES-[0-9]{6}`                                 |
| **Example** | `SES-000014`                                   |
| **Scope**   | One record in `sessions` table of `sessions.db`|
| **Generated by** | SessionManager (auto-increment, internal only) |
| **Lifetime**| Permanent DB record                            |
| **JSON key**| `sessionId`                                    |

---

### 1.3 `recoveryId`

| Field       | Value                                                        |
|-------------|--------------------------------------------------------------|
| **Format**  | `RCV-` + 8-digit date (YYYYMMDD) + `-` + 6 hex uppercase    |
| **Pattern** | `RCV-[0-9]{8}-[0-9A-F]{6}`                                   |
| **Example** | `RCV-20260921-A81F42`                                        |
| **Scope**   | User-facing identifier shown in LockScreen and Recovery UI   |
| **Generated by** | SessionManager at session creation                      |
| **Lifetime**| Permanent; primary key of `recovery_keys` table              |
| **JSON key**| `recoveryId`                                                 |
| **Note**    | Date component = UTC date of session creation                |

---

### 1.4 `recoveryKey`

| Field       | Value                                                         |
|-------------|---------------------------------------------------------------|
| **Format**  | `DEMO-` + 4 hex uppercase + `-` + 4 hex uppercase             |
| **Pattern** | `DEMO-[0-9A-F]{4}-[0-9A-F]{4}`                               |
| **Example** | `DEMO-4F9C-88A2`                                             |
| **Scope**   | Bound to exactly one `recoveryId`; one-time use               |
| **Generated by** | KeyManager (within RansomwareController)              |
| **Lifetime**| Valid until redeemed (status: `AVAILABLE` → `USED`)           |
| **JSON key**| `recoveryKey`                                                |
| **Note**    | Released to user only after `PAYMENT_CONFIRMED`               |

## SECTION 2 — SESSION STATE ENUM

### 2.1 Enumeration (10 values, in canonical order)

```
CREATED
LOCKED
PAYMENT_PENDING
PAYMENT_CONFIRMED
RECOVERY_AVAILABLE
RESTORING
VERIFYING
COMPLETED
EXPIRED
DATA_UNAVAILABLE
```

### 2.2 State Transition Table

| From State          | Allowed Next State(s)              | Trigger                                              |
|---------------------|------------------------------------|------------------------------------------------------|
| `CREATED`           | `LOCKED`                           | Sandbox encryption completes successfully            |
| `LOCKED`            | `PAYMENT_PENDING`                  | LockScreen displayed; payment timer started          |
| `PAYMENT_PENDING`   | `PAYMENT_CONFIRMED`                | MockPayment confirms payment                         |
| `PAYMENT_PENDING`   | `EXPIRED`                          | Payment timer elapses before confirmation            |
| `PAYMENT_CONFIRMED` | `RECOVERY_AVAILABLE`               | KeyManager releases `recoveryKey` to user            |
| `RECOVERY_AVAILABLE`| `RESTORING`                        | User submits valid `recoveryKey` via Recovery UI     |
| `RESTORING`         | `VERIFYING`                        | RestoreService finishes writing all restored files   |
| `VERIFYING`         | `COMPLETED`                        | All SHA-256 hashes verified against baseline manifest|
| `VERIFYING`         | `RESTORING`                        | Hash mismatch detected; retry triggered              |
| `EXPIRED`           | `DATA_UNAVAILABLE`                 | Cleanup timer fires; working\ directory purged       |
| `COMPLETED`         | *(terminal — no further transitions)*| —                                                  |
| `DATA_UNAVAILABLE`  | *(terminal — no further transitions)*| —                                                  |

### 2.3 Rules

- Only `RansomwareController` (via `SessionManager`) may write session state.
- `RecoveryBackend` (:8080) and `RecoveryPortal` are **read-only** consumers of state.
- Transitions not listed in the table above are **illegal** and MUST be rejected by SessionManager.
- `EXPIRED` and `DATA_UNAVAILABLE` are terminal error states; no recovery is possible from them.

```
PENDING

FAILED
```

### 3.2 Transition Table

| From       | Allowed Next    | Trigger                                     |
|------------|-----------------|---------------------------------------------|
| `PENDING`  | `CONFIRMED`     | `POST /api/payment/demo` succeeds           |
| `PENDING`  | `FAILED`        | Payment timeout or explicit failure         |
| `CONFIRMED`| *(terminal)*    | —                                           |
| `FAILED`   | *(terminal)*    | —                                           |

### 3.3 Rules

- Payment state is stored in `payment_events` table, column `status`.
- `MockPayment` module is the only writer of payment state.
- `CONFIRMED` payment state is required before session may advance to `RECOVERY_AVAILABLE`.

## SECTION 8 — SANDBOX BOUNDARY

### Authorized Root (HARD RULE)

```
D:\Bài tập lớn Cơ sở an toàn thông tin\Lab_sandbox\
```

### Subdirectory Structure

| Directory     | Purpose                                                                     | Write Access               |
|---------------|-----------------------------------------------------------------------------|----------------------------|
| `baseline\`   | **IMMUTABLE.** Original test files, written once by Installer. Never modified.| Installer only (setup time)|
| `working\`    | Per-session workspace. Keyed by `recoveryId` subdirectory.                  | CryptoAdapter only         |
| `restored\`   | Decryption output. Keyed by `recoveryId` subdirectory.                      | RestoreService only        |
| `manifest\`   | SHA-256 baseline manifests (JSON) and RSA key files.                        | CryptoAdapter, KeyManager  |

Example path layout:
```
Lab_sandbox\
  baseline\
    sample_document.txt
    sample_image.png
  working\
    RCV-20260923-A81F42\
      sample_document.txt.locked
      sample_image.png.locked
  restored\
    RCV-20260923-A81F42\
      sample_document.txt
      sample_image.png
  manifest\
    RCV-20260923-A81F42.json
    keys\
      RCV-20260923-A81F42_public.key
      RCV-20260923-A81F42_private.key
```

### Path Validation Rules

All components that perform file I/O MUST apply these rules, in order:

1. Receive a relative filename or path component from caller.
2. Resolve it against the authorized root using `Path.resolve().normalize()`.
3. Call `toRealPath()` or verify the canonical path string **starts with** the authorized root.
4. If the resolved path does NOT start with the authorized root → **REJECT** immediately with an error; do not proceed.
5. If the resolved path points to `baseline\` from a write-path context → **REJECT**.

**Never accept any of the following as input paths:**
- `C:\`, `D:\`, `E:\`, `F:\`, `G:\` (or any drive root)
- `Desktop`, `Documents`, `Downloads`, `AppData`, `Program Files`
- UNC paths (`\\server\share`)
- Paths containing `..` traversal after normalization
- Absolute paths supplied directly by the caller

## SECTION 9 — MODULE RESPONSIBILITIES

Each module owns exactly one domain. Violations of the MUST NOT column are bugs.

| Module                      | Owns                                                    | MUST NOT do                                                         |
|-----------------------------|---------------------------------------------------------|---------------------------------------------------------------------|
| **Pixel Chaser**            | Game logic, player/enemy state, scoring, lifecycle events (`GAME_STARTED`, `GAME_PLAYING`, `GAME_CLOSED`) | No crypto, no filesystem ops, no DB access, no payment logic       |

| **SandboxGuard**            | Path validation against authorized root, reject-on-violation | No file encryption, no file deletion, no DB access                 |
| **CryptoAdapter**           | Wraps existing `CryptoUtils` methods with sandbox-safe path logic; copies baseline→working; emits file manifest | No algorithm rewrite, no direct DB writes (reports counts to SessionManager only), no UI |
| **RansomwareController (:5000)** | HTTP orchestration, event sequencing, owns `sessions.db` via SessionManager | No crypto implementation (delegates to CryptoAdapter), no direct UI rendering |
| **LockScreen (Swing)**      | UI display of lock state, `recoveryId`, countdown timer, payment button | No filesystem ops, no DB access, no payment processing, no key generation |
| **CountdownService**        | Payment deadline timer; emits `EXPIRED` event at deadline | No file deletion, no DB writes (reports via event only), no UI     |
| **RecoveryBackend (:8080)** | HTTP bridge from browser to Controller; serves static Recovery Portal HTML | No direct DB access, no crypto, no session state writes            |
| **RecoveryPortal**          | HTML/JS UI for entering `recoveryId` and `recoveryKey`, displaying restore progress | No `recoveryId`/`recoveryKey` generation, no direct API calls to Controller (goes through :8080) |

| **KeyValidation**           | Validates `recoveryKey` format and binding to `recoveryId`; marks key as `USED` | No key generation (generation is KeyManager's domain), no crypto   |
| **RestoreService**          | Reads `.locked` files from `working\`, calls `CryptoUtils.decryptFile()`, writes to `restored\`, computes SHA-256 against manifest | No destructive ops on `baseline\`, no writes outside `restored\`  |
| **Installer**               | First-run setup: creates `Lab_sandbox\` structure, copies test data to `baseline\`, writes baseline manifest | No security bypass, no runtime encryption, no autorun/persistence  |
